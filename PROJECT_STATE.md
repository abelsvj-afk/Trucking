**Found the real reason nothing was ever live — a planning gap, not a code bug.** The owner reported a blank dark-gray screen at the Fly.io URL even after setting the Supabase secrets. Investigating turned up something more fundamental than a misconfiguration: **the repo had zero GitHub Actions workflows** (confirmed directly via the GitHub API), so nothing had ever auto-deployed, and the live Fly.io app was still running the image its launch flow built back at the original scaffold commit — while `main` had advanced roughly 30 commits past it. Setting secrets could never have fixed this: secrets restart the *existing* image, they don't rebuild from new source.

The deeper issue is that the whole plan assumed a deploy path that doesn't exist for this project's actual operating conditions. **The owner works from a phone** — no local clone, no terminal, no `flyctl`. Every "run `fly deploy`" instruction was unrunnable by the only person who runs this project. Earlier sessions (including this one) repeatedly wrote `fly secrets set` / `fly deploy` guidance that was never actionable, and the `docs/` never recorded the constraint.

Fix: added `.github/workflows/fly-deploy.yml` (new task **6.0**, not in the original roadmap). Push to `main` → typecheck + lint + unit tests → `flyctl deploy --remote-only` (remote builds, so no local Docker either). It also accepts `workflow_dispatch`, giving a "Run workflow" button in the GitHub web UI — the phone-accessible equivalent of `fly deploy`. Documented in `docs/runtime.md`'s new Deployment section, including the one-time `FLY_API_TOKEN` setup (both steps are web UIs). Verified locally that the three CI commands pass before pushing, so the pipeline's first run shouldn't fail on our own code.

**Standing lesson for future sessions, worth more than this one fix:** check that a proposed workflow is executable by the person who has to execute it, before building a plan on it. "It works if you run this command" is not a plan when the owner has no terminal.
