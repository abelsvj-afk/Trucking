**Root cause of the sign-in failure, found and fixed for real.** The `try/catch` above did its job: instead of hanging, the app surfaced the actual error via the new collapsed "Details" affordance — `@supabase/ssr: Your project's URL and API key are required to create a Supabase client!`. The owner then confirmed from the Fly.io dashboard that **both secrets were set correctly all along**, which ruled out the obvious explanation and pointed somewhere more specific.

Found it by reading the build definition rather than theorizing further. `NEXT_PUBLIC_*` values are **not** read from the environment at runtime in the browser — Next.js text-substitutes them into the client JavaScript when that bundle is *compiled*. In this deployment that compile is `Dockerfile:31` (`next build --experimental-build-mode compile`), which runs during the **Docker image build**, where Fly.io secrets do not exist (they are injected into the running machine, not the builder). Both values therefore compiled to `undefined`, permanently. `docker-entrypoint.cjs`'s container-start `--experimental-build-mode generate` pass only regenerates static HTML; it never recompiles the client bundle. That is why the site loaded fine (server code reads `process.env` at runtime, so middleware and API routes always worked) while every browser-side Supabase call failed — and why setting or re-setting the Fly secrets could never have fixed it.

Fixed by removing the dependency on build-time inlining for the browser entirely: the server reads the values at render time and injects them into the page (`src/app/layout.tsx`), and the browser Supabase client reads them back (`src/services/db/client.ts`), through a new shared module `src/services/config/public-config.ts` that documents the whole failure mode at the point of definition. That HTML *is* produced with real secrets present, because the generate pass runs at container start. Local dev is unaffected — build-time inlining still works there and the indirection falls back to it. Only genuinely public values may go in that object (it is served to every visitor in plain HTML, which is what `NEXT_PUBLIC_*` already meant); the module states explicitly that a service-role key or DB credential must never be added.
