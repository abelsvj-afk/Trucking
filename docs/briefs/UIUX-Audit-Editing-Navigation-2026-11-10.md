## 1.3 The day-log edit path, walked step by step (the centerpiece)

There are **two different editing paths** for the same duty entry, with different capabilities and different honesty properties:

### Path A — the day view (the good one, buried)
1. Home → **More** tab (tap 1) → **Fleet** row (tap 2) → **Hours of service** (tap 3). Route: `/fleet/hos`.
2. The page (`fleet/hos/page.tsx`) opens with a summary section, then the **DayLog** day view (`src/components/hud/DayLog.tsx`): a 24-hour graph for *today*, day-stepper arrows (‹ ›), the day's entries as rows with **Fix** / **Delete** buttons, and per-status totals.
3. To fix a *past* day: tap ‹ once per day backwards (no date picker, no jump-to-date, no week strip). The stepper stops at the oldest day in the carrier window; older days are only in the flat list below.
4. Tap **Fix** on an entry (or tap its stretch on the graph) → **DayEditPanel** (`src/components/hud/DayEditPanel.tsx`) opens with four separate mini-flows, each with its **own save button**: change status ("Save status"), move start time ("Move start"), insert a change inside the stretch ("Add change" — this is the only backfill), delete (two-step confirm that honestly states what status then runs on).
5. **What it cannot do:** change location, odometer, notes, load, or driver; insert a change *outside* an existing stretch (e.g. before the day's first entry or into a totally empty day — an empty day shows only "Nothing logged on this day"); add an entry on a day with no entries at all except via the full form.
6. **Edit trail in Path A: NONE.** Each action calls the plain CRUD API (`apiClient.update/create/remove` on `duty-logs`). The update overwrites `duty_status`/`started_at` in place. No reason is asked, no original is kept, no history is shown. The only provenance signals are indirect: `enteredAfterTheFact()` (created later than it started) is *displayed* in the panel, and paper-sourced rows show the remark line (`PAPER_REMARK_LINE`, `src/lib/paper-day.ts`) — honesty garnish, not a trail.

### Path B — the detail page (the form, also buried)
1. Same page, scroll past the day view to the **flat list** (newest first, up to 200 rows, `fleet/hos/page.tsx`), tap a row → `/fleet/hos/[id]` (tap 4).
2. Summary block, then a **7-field edit form** (driver, load, status, started-at `datetime-local`, location, odometer, notes — `fleet/hos/[id]/page.tsx`), one Save, then a Delete section (soft delete, restorable under "Deleted", `src/components/RecordLifecycle.tsx`).
3. **Edit trail in Path B: also NONE** — same in-place PATCH (`src/app/api/v1/duty-logs/[id]/route.ts` → generic `createCrudRoutes`, `src/services/api/crud-routes.ts`). The schema (`src/data/schemas/duty-logs.ts`) has no reason field. The table (`supabase/migrations/00011_duty_logs.sql`, plus provenance columns in 00047) stores only current values + `created_at`/`updated_at`/`deleted_at` + `source` — **no original-value preservation, no edit-history table, no annotation concept anywhere in the duty/HOS code.** (Full-text search for "annotation" across `src/lib`, `src/services`, the duty-log API, and all migrations: no matches in the duty domain.)

### Creating / backfilling today
- **New entry:** `/fleet/hos/new` — a second full 7-field form (driver picker, load picker, status, start, location, odometer, notes). From Home it's 3 taps via the Hours header button "Log duty status," or **0 extra taps for a status change only** via the Home HUD buttons (`src/components/hud/DutyHud.tsx` — driving/on-duty/off-duty/sleeper, one tap, though motion lock disables *editing* while moving; status changes stay available).
- **Backfill a forgotten entry on a past day:** either Path A's insert-inside-a-stretch (only inside an existing stretch, fixed note text "Added from the day view", no location/odometer/reason), or the full `/fleet/hos/new` form with a manually backdated `datetime-local`. Neither path says "backfill," asks why, or marks the entry as a correction beyond the after-the-fact timestamp inference.
- **Paper-log days** are a third silo: photograph → `/fleet/hos/paper/[id]` segment editor (`src/components/paper/SegmentEditor.tsx`) → save replaces the day's rows. Its corrections carry the paper remark line, and it is the most careful editor in the app — and completely disconnected from Paths A/B.

**Centerpiece verdict:** the owner is right. Fixing yesterday's mistake means: 3 taps to reach Hours, an unknown number of ‹ taps to reach the day, then a choice between a graph panel that can only change status/start with **no reason and no history**, or a 7-field form one more tap down that also keeps **no history**. The app that is becoming his ELD currently rewrites duty history silently — the exact opposite of ELD rules (49 CFR 395.30: originals retained, edits annotated).

## 1.4 The other editing flows, shorter

- **Expenses** — Money hub → list → detail: summary + inline edit form (`ExpenseEditForm`, includes the bucket picker from build #3) + delete section. The most conventional flow in the app; still 4 taps from Home to change a typo.
- **Fuel purchases** — same list→detail→form shape as expenses.
- **Pay profile** — the worst-hidden *important* thing in the app: More → Settings → scroll one long settings page to the "My pay" group. `PayTermsSettings.tsx` is genuinely good underneath (it versions terms: a correction ends the old profile `effective_to` and creates a new one — a real audit-friendly pattern the day log should learn from), but nothing labels the door "pay terms" from Money or Home; "Projected pay" shows numbers whose terms live three levels away in Settings.
- **Documents** — see §1.5.
- **Everywhere:** the detail-page edit pattern (summary → full form → delete section, all on one long scrolling page) is repeated for trucks, trailers, drivers, brokers, customers, maintenance — consistent in shape, but consistently *deep and long*: nothing edits in place, and every edit is a page navigation away from the list you were just reading.

## 1.5 Documents — what actually happens when you open one today (verified)

The owner's claim is **substantially true**, with one nuance:

1. **There is no documents home.** `/more/documents` opens on two dropdowns (Type, then Record). Until both are picked, no document is visible at all — no recent list, no "all documents," no browse. Search exists (full-text over extracted text) and is the only record-independent door.
2. **"View" is not a page.** On the Documents page and on entity pages (`src/components/EntityDocuments.tsx`, `src/components/LoadDocuments.tsx`), tapping a document shows an 88px thumbnail (images only) and a **View** button that expands `src/components/DocumentPreview.tsx` *inline on the same page*. There is **no document route** — no `/more/documents/[id]`, nothing linkable, nothing full-screen.
3. **What the preview renders:** for an uploaded **photo**, the original image full-width with an Original | Scan rendition toggle — this part genuinely works. For a **PDF** (which includes *every document the app itself creates*), the preview renders **no content at all**: filename, type label, extraction-status line, and a link "Open the original file" that leaves the app for the phone's external PDF handler. For text, a collapsed `<details>` "What the assistant reads (extracted text)" shows raw OCR text in a `<pre>` — and PDFs report "Text extraction isn't run on PDFs," so a generated document shows the owner *nothing* in-app.
4. **Generated documents specifically:** `src/services/documents/generate-document.ts` renders a `DocumentModel` (`src/lib/document-templates.ts`: title + sections of plain-text lines) to a bare text-layout PDF via `src/lib/simple-pdf.ts` behind the `DocumentGenerator` seam. The model exists only at generation time — **it is not stored** — so the app cannot re-render what it created; the PDF bytes are the only rendition, and the owner can't even see those without leaving the app. Viewer, PDF, and data are already three separate things, and two of them are invisible.

**Verdict:** documents are filed data with a photo viewer attached. There is no document *surface*: no page, no typography, no reading experience, and the app's own paperwork is the worst-served of all.

## 1.6 Is the UI piecemeal? Yes — plainly, with evidence

The owner asked for honesty here, so: **the current UI was assembled lane by lane, and it shows.** Evidence:

- **Seven sequentially-numbered stylesheets** (`src/app/styles/01-base.css` … `07-late.css`, 2,831 lines) whose filenames confess the process: `04-research-and-polish.css`, `05-motion-pass.css`, `07-late.css` are passes bolted on after the fact, not one system.
- **The palette drifted while the rule didn't.** Locked brand gold is `#c9a227`, but `--color-accent` is not a token — `07-late.css` hardcodes `var(--color-accent, #c9a227)` fallbacks, dark-scheme text gold is `#e5b83a`, button gold is `#f2b705`, light-scheme text gold is `#7a5a00`. Four golds, chosen per lane, each defensible for contrast, never unified into a named scale.
- **Components are reinvented per lane:** the HUD grew its own sheet/panel system (`hud-sheet`, `DayEditPanel`), paper logs grew `SegmentEditor`, settings grew grouped sections, hubs grew `hub-row-link` rows, detail pages hand-roll the same summary→form→delete stack with no shared `DetailPage`/`EditForm` component. Inline `style={{}}` appears exactly where a lane needed a one-off (thumbnails at 56px on one page, 88px on another for the same component job).
- **The structure grew by accretion:** two entities called "logs" (day graph vs flat list on the same page, both editable, differently), three places to change duty status (HUD buttons, `/hos/new`, day panel), two Abel doors on Home (`Ask Abel` quick action + `AskAssistant` block + the floating AbelDrop), a tab (Smart Path) duplicated as a More row.
- **What is NOT slop, and should be said too:** the accessibility discipline is real (44px targets, aria-current, skip link, teaching empty states in `ListStates.tsx`), the honesty framing is consistent (every hours surface repeats "paper-log helper, not an ELD" — `roadside-packet.ts` even hard-codes "CONVENIENCE COPY — NOT THE CERTIFIED RECORD"), the token file documents its contrast math, and the day graph itself is a genuinely good component. The bones are honest; the *assembly* is patchwork. The spec below replaces the patchwork with one system instead of adding an eighth stylesheet.

## 1.7 Friction list — ranked

1. **Day-log editing has no edit trail** — silent in-place rewrite of duty history; no reason, no original, no history view (§1.3). Blocks the "becoming his own ELD" direction outright. *(routes: `fleet/hos/[id]`, `components/hud/DayEditPanel.tsx`, `api/v1/duty-logs/[id]/route.ts`, migration 00011)*
2. **Hours is 3 taps and 2 hubs deep** — the daily-driver surface sits behind More → Fleet; past days need one ‹ tap per day with no jump-to-date. *(Home `page.tsx`, `nav-config.ts`, `hud/DayLog.tsx`)*
3. **Documents have no page of their own** — picker-before-content, no document route, PDFs (incl. everything the app creates) render nothing in-app (§1.5). *(`more/documents/page.tsx`, `components/DocumentPreview.tsx`)*
4. **Two competing day-log editors** with different powers (graph panel: status/start only, no fields; detail form: all fields, no graph context) — the owner must guess which door holds the fix he needs. *(`DayEditPanel.tsx` vs `fleet/hos/[id]/page.tsx`)*
5. **Home is eleven stacked blocks** and still lacks "Add expense" and "Find a document" in quick actions; Abel appears three times. *(`(app)/page.tsx`)*
6. **Pay terms are buried in Settings** ("My pay" group, 4 taps, one long scroll) while pay *numbers* live in Money — the terms and their results never share a screen. *(`more/settings/page.tsx`, `components/settings/PayTermsSettings.tsx`, `money/pay/page.tsx`)*
7. **Everything edits on a separate detail page**, form at the bottom of a long scroll (loads worst: form after six sections) — no in-place editing anywhere outside the day panel. *(`loads/[id]/page.tsx` and the repeated detail pattern)*
8. **Backfill has no name and no flow** — insert-inside-a-stretch with a hard-coded note, or a backdated full form; an empty day can't be started from the day view at all. *(`DayEditPanel.tsx` insertChange, `fleet/hos/new/page.tsx`)*
9. **Fleet lost its tab but kept its depth** — the parked nav decision (`nav-config.ts` header: "NOT settled") traded one problem for another: 10 fleet surfaces now cost 3–5 taps; the owner never got to rule on it.
10. **Visual patchwork** — 7 stylesheets, 4 golds, per-lane components, thumbnail sizes differing by page (§1.6). This is the "ugly" he feels, and it's structural, not a color choice.
11. **Deletes are safer than edits** — soft delete + restore exists everywhere (`RecordLifecycle`), but a *changed* value is gone forever. The safety model protects against the lesser risk.
12. **Labels that don't match the owner's words** — "Hours of service" (his words: day log), "Projected pay" vs the Home card's "Driver pay," Documents page titled by picker mechanics. Minor individually; collectively they make him hunt.

## 2.1 Principles

1. **Depth budget: 2 taps to view, 2 taps to edit, for daily things.** Anything used daily lives on Home or one tap from it; editing happens *in place* (sheet over the list), not on a separate page.
2. **One editor per thing.** The day graph becomes the only day-log editor; the detail-page form retires into it.
3. **History is never rewritten.** Every correction preserves the original and carries a reason — ELD-style (395.30-shaped), even while the app honestly remains a convenience copy today.
4. **One document, three faces, one source.** Page view, PDF, and extracted text all render from one stored document model/record.
5. **One design system** (§2.6) replaces the seven-stylesheet patchwork. Locked language only: black-and-gold, gold `#c9a227` the single accent, green = good only, red = danger only.

## 2.2 Day-log editing redesign (centerpiece)

**Surface:** `/fleet/hos` day view becomes **"Day log"** (owner's words) and the *only* editor. Changes:

- **Reach it in 2 taps:** Home gets a "Today's log" strip (today's entries, live) — tap any row → Hours day view with that entry's editor open (§2.4). Plus a date jump: tapping the day title opens a date picker / week strip; the ‹ › steppers stay.
- **One editor sheet** (evolves `DayEditPanel.tsx` into the single editor; mockup `UIUX-Mockup-DayLogEdit.html`): opens on the tapped stretch/row with **all** fields — status (4 big buttons), start time, location, odometer, notes, load — not just status/start. Three clearly-labeled modes in one sheet:
  - **Fix this entry** — change any field.
  - **Add a change I forgot** — insert a status change at any time in the day (not only inside a stretch; works on empty days and before the first entry — the sheet takes a date + time, so backfill *is* this button, named in his words).
  - **Delete entry…** — keeps today's honest consequence text ("Deleting it makes On duty run on until…") and soft delete + restore.
- **Every fix requires a reason.** One line, required, with quick chips ("Forgot to log it", "Wrong status", "Wrong time", "Entered late") + free text. The save button stays disabled without it — the same discipline the paper editor already uses for completeness.
- **Original always visible:** the sheet shows "Original: Driving from 8:05 AM (logged 8:05 AM)" before any change; the entry row afterwards carries "Edited 9:12 AM — 'Forgot to log the fuel stop'"; tapping it opens **Edit history** for that entry (below).
- **Motion lock unchanged:** while moving, editing stays off (DutyHud rule), status changes stay on.

**Data changes — migration 00087 (next free number; 00086 is latest):**
- New table `duty_log_edits`: `id`, `company_id` (tenant RLS, same pattern as 00011), `duty_log_id` → duty_logs, `kind` (`update` | `insert` | `delete` | `restore`), `reason text not null`, `before jsonb` (full row snapshot before; null for insert), `after jsonb` (full row snapshot after; null for delete), `edited_at timestamptz` (when the fix was made — distinct from the entry's own times), `source` (`app` | `conversation` | `paper` — Abel-made and paper-made fixes land in the same trail).
- Inserts created by "Add a change I forgot" are normal `duty_logs` rows whose first `duty_log_edits` row is `kind='insert'` with the reason — a backfill is a first-class, explained entry, not a fake "Added from the day view" note. The `notes` hardcode dies.
- **Write path:** extend `src/app/api/v1/duty-logs/[id]/route.ts` (and the collection route for inserts) beyond the generic CRUD factory: PATCH/DELETE/POST accept `edit_reason`, snapshot before/after in the same transaction (the factory's existing `validateMerged`/`prepareUpdate` hooks in `crud-routes.ts` are the seam — no new framework). Server **rejects** a duty-log mutation without a reason (except a live status change from the HUD, which is a *new entry*, not an edit — creating the current status is logging, not correcting).
- **Read path:** `GET /api/v1/duty-logs/[id]` gains `edits: [...]` (or a sibling `/edits` route); the editor sheet and an "Edit history" section render it. `enteredAfterTheFact` stays as a derived label, now backed by real data.
- **Paper logs:** saving a paper day (`/fleet/hos/paper/[id]`) writes its rows with `kind='insert', source='paper'` trail rows, and the existing `PAPER_REMARK_LINE` discipline extends: any later fix to a paper row shows the same line. No change to the paper editor's completeness gate.
- **Roadside packet:** the packet builder (`src/lib/roadside-packet.ts`) gains one line per edited entry in the period ("Edited — original retained in the app"), keeping the CONVENIENCE COPY framing word-for-word otherwise. An officer sees that corrections exist and are annotated — which is what a real ELD shows — without the app claiming certification.
- **Abel parity:** Abel's existing duty-log write tools must pass a reason too (his proposals already carry explanations to the owner — that text becomes the stored reason on the owner's yes). Same trail, every surface.

**What does NOT change:** `lib/hos.ts`, `lib/hos-cycle.ts`, the window endpoint, the carrier config — the clocks compute from current rows exactly as today. The trail is additive storage and UI; it never feeds the math.

## 2.3 Documents — a real viewer (one source, three faces)

**New route: `/more/documents/[id]`** — a full-screen document page (mockup `UIUX-Mockup-DocumentViewer.html`):

- **Chrome:** back link to where you came from (load/expense/Documents), title + kind + filed-against + date, Share, and a rendition toggle: **Page | Original photo | Scan** (Original/Scan already exist in `DocumentPreview.tsx` — they move here).
- **Page face (the new thing):** the document rendered as a formatted page — white paper sheet on the dark chrome, real typography (firm header, meta grid, route/parties block, line-item table, totals, requirements, signature line). This is a *reading* surface, phone-first.
- **One source of truth:** rendering splits by what the document *is*, never by hand-maintained copies:
  - **App-created documents:** store the `DocumentModel` at generation time — new nullable `documents.model jsonb` (migration 00087, same migration as §2.2) written by `generate-document.ts` alongside the PDF bytes. The Page face renders the model as HTML; the PDF generator renders *the same model* to PDF (it already does — `documentModelToText`/`appPdfGenerator` consume exactly this structure); extracted text derives from the model (`documentModelToText` already exists). Model is the truth; page and PDF are two renderings; they cannot diverge because neither is stored as content.

## 2.9 Truck navigation — scoping (owner requirement 2026-11-10; design + source choice in this round, build sequenced after Home approval)

**The owner's ask, in substance:** today the Home map shows GPS position, the truck icon, and roads — no route line, no guidance. He wants navigation that knows the active load, draws the real route to its next stop with a turn list and live ETA, respects his truck's physical profile, never routes a U-turn while a trailer is attached, follows him as he drives, and re-routes on deviation.

**What the code actually has today (verified 2026-11-10 — the premise needs one correction):** the app is *not* starting from zero, and the spec says so plainly rather than rebuilding what exists.

- **A truck-aware routing layer already exists** (`src/services/integrations/routing.ts`), built for Smart Path behind a provider interface with an honest chain: **(1) OpenRouteService `driving-hgv`** — a real HGV profile (truck road-access filtering + the truck's own dimensions as restrictions), primary *only when the free `ORS_API_KEY` is set* (it skips itself, with a logged note, when absent — whether the key is set on Fly today is a deploy-time verify item for King); **(2) Valhalla `truck` costing** on the public FOSSGIS endpoint (`valhalla1.openstreetmap.de`) — truck-legal and keyless, a community demo service with no quota/SLA, so fallback by design; **(3) OSRM public demo** — a **car** profile, last resort, whose results are stamped `truckLegal: false`. Every provider response is Zod-validated.
- **Smart Path already has a Drive mode** (`src/lib/drive.ts`, `drive-reroute.ts`, `route-progress.ts`, `drive-maneuver-speech.ts`; `/smart-path/drive`) with hard honesty gates already in force: a car-profile plan (`truckLegal === false`) **can never enter Drive — no override exists**; progress comes only from real GPS fixes; hours shown are labeled projections. The Home map component (`DriveMap.tsx`, MapLibre) **already knows how to draw a route line** with the driven part dimmed.
- **So why does he see no route?** Because the only route Home can draw comes from a **Smart Path checked run saved in that phone's localStorage** (`src/lib/use-active-route.ts` — drawn only if the run belongs to a still-confirmed load and is ≤72h old). If he didn't plan the trip in Smart Path on that device, there is no route — position + heading only, **never an invented line**. The missing piece is not a routing engine; it is the connection **active load → route, automatically**, plus guidance on the everyday map surfaces. That is exactly what this workstream builds — on the existing layer, not beside it.

**N1 — Active load as first-class shared state (foundation; build first; it also serves Abel).** Today "active load" is a *heuristic re-derived in three places*: `pickActiveLoad()` (`src/lib/active-load.ts` — earliest upcoming `confirmed` load by dates) feeds Home's Active load card and `pay-summary.ts`, while Abel's snapshot (`src/services/bot/store.ts`) carries its own `activeLoads` list. Dates can point at the wrong load, and app and Abel can disagree. The design: an explicit, stored pointer — **one row per driver** (new table, migration numbered at build time: `company_id`, `driver_id`, `load_id`, `set_at`, `set_by` — app or Abel), with **current leg and next stop derived, never stored twice**: next stop = the first `load_stops` row (00062, seq order) with `departed_at` still null (an `arrived_at` with no departure = "you are at this stop"); current leg = from the last departed stop (or current position) to that next stop; a load without stop rows falls back to its `destination`. **Set:** the driver taps **Make active** on the load page / loads list, tells Abel ("make Trip 1874 my active load" — new Abel tool on the same row), or accepts the app's suggestion (the existing `pickActiveLoad` heuristic survives *only* as the suggestion when no explicit pointer exists — labeled a suggestion, never silently treated as his choice). **Cleared:** automatically when the load is completed/cancelled, or when he makes another load active. **Read:** one shared server helper (`getActiveLoad`) that Home, Money/pay, Smart Path, and Abel's snapshot all call — the three derivations collapse into one truth.

**N2 — Route to the load.** With an active load set, the app computes the route **from his current position to the next stop** through the existing provider chain (server-side, via the route-check pattern — nothing stored but a cache of the stop's geocode: stop rows carry addresses, not coordinates, so the first route for a stop geocodes its address via the existing `src/services/integrations/geocoding.ts` and caches lat/lng on the stop row — small migration at build time). The Home map draws the geometry through `DriveMap`'s existing route layer (driven part dimmed, via `route-progress.ts`); a **turn list** (the providers already return normalized maneuvers — `RouteManeuver` in `routing.ts`) opens from the map's route caption; **ETA / distance remaining** recompute from remaining geometry as fixes arrive. The `truckLegal` gate is inherited unchanged: if only the OSRM car profile answers, the map shows Smart Path v1's car-route warning wording and **guidance does not engage** — never a car route dressed as a truck route, and never a straight line.

**N3 — Truck-aware constraints.** The truck profile **already lives** on the `trucks` record — `height_in`, `length_in`, `weight_lbs` (plus governed speed, tank, MPG) — edited at **Fleet → Truck profile** (`/fleet/truck-profile`, shared `TruckProfileFields.tsx`) and already passed to both truck engines as restrictions. Two honest gaps, named rather than papered over: **width is not captured** on the truck today (engines accept it; until the field exists, width checks rest on OSM road data alone), and **trailer dimensions are not captured at all** (`trailers` carries type only) — the nav build adds width to the truck profile fields and height/length to the trailer editor, and until a dimension is recorded the profile's own rule holds: **empty means "not captured yet" — nothing invents a default**, and a route computed with missing dimensions says so ("truck size not fully set — clearances checked against road data only"). **Trailer-attached vs bobtail is derived, never a manual toggle:** attached = an active load exists whose pickup stop has departed and whose final delivery has not (equivalently: he is under a load); bobtail = no active load, or after the final delivery departs. **No U-turns while trailering — stated honestly as an app-level rule, not an engine feature:** neither ORS nor Valhalla exposes a "no U-turn" switch. The app enforces it on the returned maneuvers: if a U-turn maneuver appears while trailering, the route is re-requested with a via-point placed past the turn so the truck loops the block; after two failed attempts the route is shown **with the U-turn flagged in words** ("includes a U-turn at … — could not route around it"), never hidden. Bobtail relaxes the rule (a U-turn maneuver is allowed and shown as one).

**N4 — Guidance behavior.** Reuse Drive mode's evaluation machinery (`drive.ts` session evaluation, `drive-reroute.ts` deviation thresholds, the closed maneuver-prompt set) on the Home map rather than writing a second guidance engine: the **next-turn prompt** (arrow, distance, road name) rides the map as a card; off-route beyond the existing thresholds triggers a re-route through the chain (N2) with the new ETA; arrival at a stop is detected from fixes the way Drive already does it — and stop progress (`arrived_at`/`departed_at`) is still only ever set by his taps, per 00062's rule — guidance *suggests*, it never records. **One maneuver state feeds every map mode** (the addendum surfaces): normal Home map (prompt card on the map), full-screen (same card, larger), collapsed (the map is away — the "Show map" handle bar carries the next-turn line in text), floating overlay (the Tracker overlay's status card gains the next-maneuver line beside the clocks). Voice prompts stay inside Smart Path Drive for this round; the Home surfaces are visual.

**N5 — Source choice (free-first, as ruled).** **Recommendation: keep the existing chain — set the free ORS key, Valhalla keyless as fallback — and build no new routing integration in v1.** Reasoning: it is already built, Zod-validated, and carries the `truckLegal` honesty model end-to-end; ORS `driving-hgv` on the free Standard plan (2,000 directions/day, 40/min, per the published plans page cited in `openrouteservice.ts`) is far beyond one truck's re-route volume; Valhalla's truck costing makes the app truck-legal even with no key. **Limits, plainly:** "truck-legal" here means *checked against the restrictions recorded in OpenStreetMap data* (maxheight/maxweight/hgv tags + his dimensions) — OSM coverage is incomplete, a road with no recorded limit is treated as passable, and the codebase's own rule stands: **the truck's own nav/ELD stays the final word**. **Paid truck providers evaluated and deferred, not dismissed:** HERE Routing and TomTom Orbis truck routing (both paid, per-request; restriction data beyond OSM, fleet-grade) and Trimble PC*Miler (the industry standard for truck routing, enterprise pricing) — each would be a new integration + a recurring bill to fix a coverage problem that hasn't bitten yet; revisit the day an OSM-blind route actually misleads him, with the provider interface making the swap a chain change, not a rewrite. Self-hosting Valhalla later (the client already honors `VALHALLA_URL`) removes the demo-service dependency if volume or reliability ever demands it — no code change, an ops decision.

**Abel tool decision (standing rule — stated for this feature):** Abel reads and sets the same active-load pointer by conversation — `get_active_load` (load, current leg, next stop, ETA when a route exists), `set_active_load` (by trip number / load description, resolving to exactly one load or asking), `clear_active_load`. These ship WITH N1, routed through dynamic tool selection (PR #47 pattern); Abel never keeps a private notion of the active load.

**N6 — Abel location-aware place search (owner addendum 2026-11-10; sequences with N1→N2).** The flow: on Telegram he asks "Where's the closest Love's?" (or any place/category) → Abel answers the nearest match + distance from his current position → Abel offers "Want me to add that stop to your Smart Path?" (yes/no by button or text — his tap is the control) → on YES the stop joins the Smart Path run and the route redraws through it with refreshed ETA/distance; on NO nothing changes.
- **Position truth:** Abel reads the latest `driver_positions` row via `GET /api/v1/position` — the endpoint that already returns the newest fix (Tracker device feed or Telegram Live Location) **plus its age in seconds** — the same store the Tracker overlay's `POST /api/v1/position/clocks` and the Home "Phone GPS · just now" caption read. The answer carries the fix's age whenever it is not fresh, and when tracking is off Abel answers from the last known ping **and says so in words** ("last ping 42 minutes ago — tracking is off"). A stale position is never presented as live.
- **Ping on demand (owner addendum, same day — "Can it not shoot a new ping if it needs to?": yes, built that way).** The lookup flow is age-first: read the fix's age → **fresh** (≤ 120 seconds: at 65 mph two minutes is ≈2.2 miles — beyond that an answer can name an exit he has already passed) → answer from it. **Stale** (> 120 s) → Abel requests a fresh fix before answering: the server sends a wake to the Tracker app, the Tracker grabs a one-shot GPS fix and posts it to the same device feed, and Abel waits up to **45 seconds** (a one-shot fix typically lands in 5–20 s; 45 s keeps the Telegram turn inside conversational patience) for a fix newer than the request before answering from it. **Fallback honesty, unchanged and age-labeled:** if no fresh fix lands inside the wait — phone off, no signal, the OS blocked the wake — Abel answers from the last known position and labels its age ("last ping 22 minutes ago"), never silently stale. Wakes are rate-limited (one outstanding per driver, ≥ 3 minutes between wakes) so repeated asks can't spam the phone's battery or the push channel.
- **Split shipping — stated plainly so the interim is never oversold:** the wake channel does not exist yet. `device_tokens` (00073) are *inbound* feed-auth tokens; there is **no outbound push infrastructure (no FCM sender, no push-token registry) in the codebase today**. So: the **Abel/server side** — age check, wake-request record, wait, labeled fallback, and a new `request_fresh_fix` tool — ships WITH the navigation build, and until the Tracker piece lands it degrades to exactly the age-check + labeled-fallback behavior (the wake request is recorded and expires unanswered; Abel's wording stays honest). The **Tracker side** — FCM push-token registration (a new token kind, distinct from the feed token), the wake-and-fix handler (high-priority data message → one-shot fix → post), plus the server FCM send path and its Firebase credential as an ops item — ships with the **next Tracker release**, the same release carrying the floating map window (§2.4) and the permanent-keystore signing (the one needing his uninstall/reinstall). Even with FCM, a force-stopped or OEM-killed app may not wake — the labeled fallback is permanent, not a placeholder.
- **Places source (existing, no new integration):** `src/services/integrations/places.ts` — OpenStreetMap via Overpass, keyless, behind the `PlacesProvider` interface, Zod-validated, with the file's own honest limits (a place exists in OSM near the point; OSM rarely carries price/hours/truck-access — never invented). Today its kinds are fuel / grocery / fast_food / gym / rest_area, queried near route points. N6 extends it, it does not replace it: a `findNearest(point, kindOrName)` shape for a single position, and **truck-relevant kinds become first-class** — truck_stop (Love's, Pilot/Flying J and independents by name/brand tags), rest_area, walmart (grocery covers generic; Walmart by brand), fuel. Where OSM tags carry truck facts (`hgv`, parking, brand), the answer relays them as recorded; where they don't, the answer says the data doesn't know — never a guess about truck parking.
- **Detour honesty:** when a route to the active load (§2.9 N2) exists, the answer states on-the-way vs detour **with the added miles and time** (computed by re-running the route through the stop via the N2 chain — approximate, labeled with the routing source's limits from N5). No active route: distance-only answer, no invented detour math.
- **Smart Path write:** the YES writes into the same checked-run model Smart Path already uses (the run Home draws from, `use-active-route`) as an added stop — one write path, so the map, Smart Path, and Abel can never disagree about the plan. If no run exists, Abel says so and offers to start one from the active load instead of silently creating a divergent plan.
- **Abel tool decision (this addendum):** `read_current_position` (latest fix + age + live/stale label — the ONLY position read Abel's answers may cite), `request_fresh_fix` (the ping-on-demand wake: records the request, waits ≤ 45 s for a newer fix, returns the freshest fix + its age + whether the wake landed — server side ships with N6; the Tracker wake handler is the next-Tracker-release item above), `find_nearest_place` (place or category → nearest matches with distance, truck facts as recorded, detour math when a route is active), `add_stop_to_smart_path` (executes ONLY on the owner's yes to the offer — the offer itself is the proposal; a bare place question never writes anything). All routed through dynamic tool selection; all ship with N6.

**Sequencing:** N1 → N2 → N3/N4, as **its own lane after the Home surface is owner-approved** (per the owner's sequencing): own branch, own migration(s) (active-load pointer; stop geocode cache; profile-field additions), full gate, and the same honesty tests extended — a car-profile route provably cannot engage guidance, a U-turn provably flags under a trailer, and Abel and Home provably read the same active load. The corrected Home mockup shows the map's navigation state only (route line + next-turn card) — the honest representation of N2/N4's surface, labeled as scoped-not-yet-built there and here.

## 2.10 Documents workstream expansion — scanner, smart packets, roadside packet (owner, 2026-11-10 later; SCOPING — builds as its own lane after this redesign lands)

**The owner's framing, which governs all three: the app is his PROOF VAULT.** He tracks miles and everything while working for someone else; if anything goes sideways he asks Abel and the packet is there instantly. Later the same vault is his own company's system. Grouping accuracy is therefore a *correctness* feature: a document filed under the wrong load is a defect, not a nicety.

### 2.10.1 Real-document rule + print (BUILT in this round — see §2.3)

Anything that is a document renders like a real document (the white-paper Page face) and prints as the document itself — clean print output of the document, never a screenshot of app chrome. Specified in §2.3 and built with the document viewer in this redesign.

### 2.10.2 In-app scanner (scoped; builds after the redesign)

**What exists today (verified in code):** the hard half is already built and running server-side. Every uploaded photo (app upload or Telegram intake) passes `src/services/documents/process-document.ts` → `scan-image.ts` → `pixels.ts`, which already implements: EXIF rotation, document **corner detection** (quad finding on the grayscale image), **perspective warp** (full homography solver, `warpPerspective`), contrast stretch → black-and-white enhancement (`enhanceScanPixels`), and blur scoring. The Scan rendition the viewer shows is that pipeline's output. Paper-log capture already uses the camera (`capture="environment"` on `/fleet/hos/paper`).

**What is missing — the capture experience, not the processing:** a CamScanner-style in-app flow: open the scanner from Documents / a load / a packet → live camera view with a document guide frame → capture → the photo runs the existing server pipeline → the owner sees the straightened Scan beside the Original and confirms (retake / keep both) → it files into the context he opened the scanner from. Original photo is ALWAYS retained alongside the scan (the existing Original/Scan two-rendition model — unchanged).

**Honest limits, stated now:** (a) Live edge-detection overlay + auto-capture in the browser would need client-side CV (OpenCV.js-class, a multi-MB wasm download — wrong on a truck-stop connection); v1 therefore guides with a frame + tap-to-capture and lets the proven server pipeline find the corners — the result is the same corrected scan, the guidance is simpler. (b) If the pipeline finds no confident quad it already degrades honestly (enhancement without warp); the scanner UI must say so ("couldn't find the page edges — scan is contrast-enhanced only") and offer a manual four-corner adjustment as a v1.1 candidate (requires the pipeline to expose/accept a quad — small server change, scoped, not in v1). (c) getUserMedia needs HTTPS + permission and falls back to the file-capture input where unavailable (the paper-log pattern). (d) Nothing here needs the native Tracker app; if a future native scanner is wanted it reuses the same server pipeline and rendition model.

**Abel tool decision (standing rule):** capture itself is a camera act — no Abel tool can or should take the photo. Abel gets ONE small new tool, `request_scan`: in conversation he can ask for a named document into a named context ("scan the signed BOL into Trip 1874's packet") and the app surfaces the scanner deep-linked to that context. Placement confirmation ("filed under Trip 1874's packet") rides the packet reads in §2.10.3. Telegram photo intake already lands scans today and keeps working unchanged (parity).

### 2.10.3 Smart packets (scoped; builds after the redesign)

**Shape:** a packet is a labeled group of documents bound to one load (later: other entities), shown as its own folder card in the Documents area with the load's state on the label (active / complete / done / cancelled — read from the load's status, never a second copy of it). Documents arrive already attached to records (`documents.related_entity_type/id`); a packet is the load-scoped *view + label + set operations* over that existing attachment, not a new filing silo: packet contents print individually or together (one combined print view, §2.3's print rule), and email individually or together (one message, the set attached).

**Grouping discipline (the correctness bar):** documents Abel can bind with certainty (uploaded against the load, created from the load, scanned into the load's context, or carrying the load's identifiers in extracted text — trip number, broker ref, addresses) group automatically and SAY why on the packet ("placed here: mentions Trip 1874 / ITS Logistics ref"). Anything uncertain is a **proposal** in the existing proposal discipline — owner sees the reasoning and says yes/no; nothing files silently. A document Abel cannot place sits in an **Unfiled** tray on the Documents landing, visible, never force-grouped. Re-filing a document to another packet is an owner-confirmed move with the reason kept (same honesty pattern as the edit trail).

**Abel tool decision:** new tools ship with the feature, routed through dynamic tool selection (PR #47 pattern): `list_packets`, `get_packet` (contents + load state + each item's placement reason), `assemble_packet` (create/label/regroup — proposal-gated), `propose_document_filing` (uncertain grouping → proposal with reasoning), `email_packet` and `email_document` (send the set or the single document — existing email proposal discipline: propose → owner yes → send, owner@ only per standing rules). Print is an owner-in-app act: Abel prepares the set and names the packet; he does not claim to print.

### 2.10.4 Roadside / DOT packet as a real document (scoped; builds on PR #48 — do NOT duplicate its machinery)

**What exists today:** the roadside lane (PR #48, migration 00086 `roadside_packets`) already builds the inspection packet from the one HOS read, emails it as a set (`prepare_inspection_packet` / `send_inspection_packet` / `send_inspection_packet_to_me`), and the web roadside page shows it in-app — all stamped "CONVENIENCE COPY — NOT THE CERTIFIED RECORD."

**The upgrade (presentation + one content addition, no new machinery):** (a) the packet renders through the document system — the same white-paper Page face as §2.3 — in-app and in the emailed rendering; (b) the packet gains a **day-log snapshot WITH the graph**: the 24-hour graph lines for today + the prior 7 days rendered as part of the packet document (today the officer-facing packet lists entries; the graph is the at-a-glance proof), drawn from the same window read the packet already takes — graph rendering must be shared code with the Day log page so the picture can never diverge; (c) print preview shows exactly what prints, graph lines included (the §2.3 print rule applied to the packet). The CONVENIENCE COPY framing stays word-for-word; edited entries carry the §2.2 "Edited — original retained" line inside the snapshot.

**Abel tool decision:** NO new tools — parity plus content upgrade. Abel's existing build-#4 tools (`prepare_inspection_packet`, `send_inspection_packet`, `send_inspection_packet_to_me`) keep their names, proposal discipline (email always proposes), and surfaces; they return the document-styled packet with the graph snapshot. The parity gate for that lane re-runs Abel's roadside flows end-to-end against the upgraded rendering.

**Sequencing for §2.10:** scanner → packets → roadside-document, as ONE lane after this redesign merges and its migration (00088) is live (the lane's own migration numbers follow whatever is next; packet grouping needs no new tables in v1 — packets derive from existing attachments; if a label/override store proves necessary it lands as that lane's numbered migration). Each item ships with its Abel tools above and a parity + tool-decision line in its landing report, per the standing rule.
