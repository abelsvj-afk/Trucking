# Data Schemas

Phase 6 deliverable per `MASTER AI ENGINEERING & SYSTEM DEVELOPMENT WORKFLOW`. This is a contract: once implementation starts, code conforms to this, not the other way around. Covers the MVP entities from `docs/requirements.md`, built on the relational, `company_id`-scoped approach decided in `docs/architecture.md`.

## Global conventions (apply to every table below)

- **Primary key:** `id`, UUID, generated by the database.
- **Tenant scoping:** every table has a `company_id` (UUID, references `companies.id`, not null). Row-level security restricts every query to the caller's own `company_id` — this is the architectural decision from `docs/architecture.md`, applied concretely.
- **Timestamps:** every table has `created_at` and `updated_at` (both `timestamptz`, defaulting to now, `updated_at` maintained on write).
- **Soft delete:** every table has a nullable `deleted_at` (`timestamptz`). Deleting a record sets this instead of removing the row — per the workflow doc's "reversible actions beat irreversible actions" principle and the reliability requirement in `docs/requirements.md` that data must never be silently lost. Deleted records are excluded from normal reads but never physically erased. (No user asked for a stricter "no permanent deletes" rule in `docs/governance.md` — this is the ordinary engineering default for financial data, not an extra restriction.)
- **Money:** stored as integer cents (not floating point), to avoid rounding errors in financial figures.

Recurring/preventative maintenance, as distinct from `maintenance_events`' record of work already done. Added per the owner's explicit request after seeing a real breakdown story (a degraded trailer electrical connection) that a scheduled inspection would likely have caught — the gap being that `maintenance_events` only lets you log what already broke, never what's coming due.

## pretrip_inspections

A log of pre-trip walkaround inspections — the DOT-style practice of checking tires, lights, brakes, coupling, etc. before driving. Deliberately does **not** model the checklist itself as data: the list of things to check is a fixed set rendered in the UI (see `docs/design/ui-ux.md`), not a per-company-customizable table, since it's a standardized practice rather than something that varies meaningfully per fleet at this scale. Only the outcome of running through it is stored.

## duty_log_edits

Added by migration `00088` (UI/UX redesign spec 2026-11-10 §2.2). The day log's edit trail: one row per CORRECTION of a duty entry — an update, a backfilled insert, a delete, a restore — carrying why it happened and the full row before/after. Live logging (a new entry for the status starting now) is not a correction and writes no row. The trail is additive storage only: HOS math never reads this table, and existing duty rows have no trail (their history starts at "Original entry created" from `duty_logs.created_at`; nothing is backfilled). Tenant-isolated via RLS (`private.current_company_id()`), like every table.
